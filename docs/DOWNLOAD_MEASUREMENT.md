# 내부·외부 다운로드 측정

## 목적

동일한 Windows 무선 단말에서 다음 두 경로의 다운로드 처리량을 분리해 기록합니다.

```text
내부망: 단말 → AP → WLAN 컨트롤러/터널 → 사내 유선망 → 내부 기준 서버
외부망: 단말 → AP → 사내망 → 회사 프록시 → 인터넷 경계 → 외부 사이트
```

외부 측정값의 의미는 **회사 프록시를 포함한 외부 서비스 체감 다운로드 속도**입니다. 프록시 서버 내부 CPU, 세션, 큐, 캐시와 정책 상태는 확인하지 않으므로 프록시 장애로 단정하지 않습니다.

## 사용자 실행 경계

- 프로그램 시작만으로 측정하지 않습니다.
- 사용자가 `내부망 측정 시작` 또는 `외부망 대상 순차 측정`을 눌러야 실제 네트워크 요청이 발생합니다.
- 내부와 외부 모두 HTTP/HTTPS `HEAD` 및 `GET`만 사용합니다.
- 요청 본문을 받는 API가 없으므로 파일 업로드나 업로드 속도 측정 경로가 없습니다.
- 수신 본문은 고정 크기 버퍼에서 읽고 즉시 폐기합니다.
- 측정 본문, WLAN 정보와 결과를 외부로 전송하지 않습니다.

## 내부망 측정

내부 URL은 한 개 입력합니다.

- `DIRECT` 또는 명시적 프록시 바이패스가 기대 경로입니다.
- 프록시 경유로 판정되면 요청을 보내지 않고 `기대 경로 불일치`로 종료합니다.
- 내부 서버, NIC, 디스크·메모리와 상위 링크의 성능도 결과에 포함될 수 있습니다.
- 안정적인 고정 크기 파일을 제공하는 승인된 내부 HTTP/HTTPS 서버를 사용해야 합니다.

## 외부망 측정

외부 URL은 한 줄에 하나씩 최대 네 개 입력합니다.

- 현재 로그인 사용자의 수동 프록시, PAC 또는 WPAD 정책을 URL별로 적용합니다.
- 외부 대상이 `DIRECT`로 판정되면 회사 프록시 경로와 다르므로 요청 전에 중단합니다.
- 각 URL을 입력 순서대로 측정해 여러 외부 사이트에 동시에 부하를 주지 않습니다.
- 서로 다른 사이트 또는 CDN의 승인된 고정 파일 URL을 둘 이상 사용해야 공통 외부 경로와 개별 사이트 편차를 구분하기 쉽습니다.

## HEAD 사전검사

기본값은 사용입니다.

1. HEAD 요청으로 상태, 프록시 경로와 리다이렉트를 확인합니다.
2. 서버가 HEAD를 `405 Method Not Allowed` 또는 `501 Not Implemented`로 거부하면 GET 측정으로 계속합니다.
3. 인증·정책 오류, 안전하지 않은 리다이렉트와 경로 불일치는 GET 전에 종료합니다.

HEAD 응답이 성공하더라도 GET 결과가 같다고 보장하지 않으므로 실제 성능값은 GET에서만 계산합니다.

## 최대 수신량과 스트림

공통 설정의 최대 수신량은 **대상 URL 하나당** 적용됩니다.

- 스트림 1개: 전체 상한을 한 연결에 적용
- 스트림 2~4개: 전체 상한을 스트림 수로 분배
- 나머지 바이트가 있으면 앞쪽 스트림부터 1바이트씩 추가
- 모든 스트림의 실제 수신량 합계가 대상별 MaxBytes를 초과하지 않음

예를 들어 최대 100MB, 스트림 4개이면 각 스트림은 약 25MB를 받습니다. 외부 URL 3개를 순차 측정하면 전체 실행의 최대 수신량은 300MB입니다.

## 리다이렉트 검증

WinHTTP 자동 리다이렉트를 끄고 상위 측정 계층이 직접 추적합니다.

각 Location마다 다음을 다시 확인합니다.

- HTTP 또는 HTTPS 절대·상대 URL 해석
- URL userinfo와 fragment 차단
- 외부 HTTPS 요청의 HTTP 다운그레이드 차단
- 외부 localhost, 루프백, 사설, 링크 로컬, 예약 주소 차단
- 내부 DIRECT·외부 PROXY 기대 경로 재확인
- 사용자 지정 최대 리다이렉트 수

URL query는 결과 화면에서 `[마스킹됨]`으로 표시합니다.

## 기록 지표

- 대상 이름과 내부·외부 구분
- 시작·종료 시각과 전체 소요시간
- 성공, 부분 성공, 실패, 시간초과, 취소, 정책 차단, 인증 실패, 경로 불일치
- 실제 수신 바이트
- 전체 평균 Mbps
- 1초 단위 및 마지막 잔여 구간 Mbps
- TTFB
- HTTP 상태 코드
- 실제 프록시 사용 여부
- 요청·완료 스트림 수
- 리다이렉트 수와 마스킹된 최종 URL
- `Age`, `Via`, `Cache-Status`, `X-Cache`, `Content-Length`, `Content-Range`, `ETag`, `Last-Modified`

`Via` 값은 프록시 호스트 정보를 포함할 수 있어 WPF 화면에서는 원문 대신 `[설정됨]`으로 표시합니다.

## 캐시 해석

`Age`, `Via`, `Cache-Status`, `X-Cache`가 있으면 프록시 또는 중간 캐시 가능성을 판단하는 참고자료로 사용합니다. 헤더가 없다고 캐시가 없다고 증명할 수 없으며, 캐시 적중 결과는 외부 원본 서버까지의 전체 경로 성능을 대표하지 않을 수 있습니다.

## 실패 해석

다음 상태는 낮은 Mbps로 변환하지 않습니다.

- `401`: 원격 사이트 인증 필요
- `403`: 사이트 또는 정책 접근 거부
- `407`: 프록시 인증 필요·호환 실패
- `429`: 사이트 요청 제한
- DNS·TCP·TLS·WinHTTP 오류
- 제한 시간 초과
- 안전하지 않은 리다이렉트
- 내부/외부 기대 프록시 경로 불일치

일부 병렬 스트림만 성공한 경우 `부분 성공`으로 표시하고 완료 스트림 수와 실제 수신량을 함께 기록합니다.

## 취소 동작

취소 버튼은 취소 토큰을 설정합니다. 동기 WinHTTP Native 호출 자체를 강제로 종료하지 않으므로 현재 호출이 반환된 후 다음 리다이렉트, 다음 스트림 처리 또는 다음 외부 대상부터 중단됩니다. 화면에는 `취소 요청됨`과 최종 취소 상태를 구분해 표시합니다.

## 자동 테스트

GitHub Windows runner에서는 실제 외부 사이트나 회사 프록시를 사용하지 않습니다.

- 내부 측정: `127.0.0.1` 합성 HTTP 서버
- 외부 측정: `example.invalid` URL을 `127.0.0.1` 합성 프록시에 전달
- 상대 리다이렉트, HTTPS 다운그레이드, 외부 로컬 주소 차단
- HEAD·GET, 선택 헤더, TTFB, 평균·구간 처리량
- 2스트림 전체 MaxBytes 상한
- 사전 취소와 잘못된 경로 설정
- 본문 수신 시간초과

실제 WLAN, 내부 서버, 회사 프록시·PAC·WPAD, TLS 검사, GPO와 EDR은 사용자가 로컬 환경에서 검증합니다.
