# 브라우저 관찰 샘플 시간 연속성 보호

브라우저 관찰은 같은 물리 Wi-Fi 인터페이스의 누적 수신·송신 바이트 차이를 실제 카운터 시각 간격으로 나눠 Mbps를 계산합니다. 드라이버 정지, 절전·저전력 전환, 높은 시스템 부하 또는 스케줄러 지연으로 샘플 간격이 지나치게 길어지면 하나의 정상 실시간 구간처럼 계산하면 안 됩니다.

이 기능은 각 카운터 스냅샷을 처리량 샘플로 만들기 전에 타임스탬프 연속성을 확인합니다.

## 고정 판정 규칙

```text
허용 상한 = max(5초, 예상 샘플 간격 × 4)
```

관찰 옵션에서 허용되는 예상 샘플 간격은 500~2000ms입니다.

| 예상 간격 | 허용 상한 |
|---:|---:|
| 500ms | 5초 |
| 1000ms | 5초 |
| 1500ms | 6초 |
| 2000ms | 8초 |

허용 상한과 정확히 같은 간격은 유지합니다. 상한을 초과한 경우에만 중단합니다.

다음 간격도 중단합니다.

- 현재 타임스탬프가 이전 타임스탬프와 같음
- 현재 타임스탬프가 이전보다 과거임

## 처리 순서

```text
고정 물리 Wi-Fi 카운터 읽기
  ↓
고정 인터페이스 ID 재검증
  ↓
이전·현재 카운터 타임스탬프 비교
  ├─ 0 이하 → 중단
  ├─ 허용 상한 초과 → 중단
  └─ 허용 범위 → 바이트 델타와 Mbps 계산
```

시간 단절 판정은 현재 카운터를 `BrowserObservationSample`에 추가하기 전에 수행합니다. 따라서 비정상적으로 긴 구간에 누적된 바이트는 다음 값에 포함되지 않습니다.

- 평균 조정 수신 Mbps
- 최고 조정 수신 Mbps
- 총 수신 바이트
- 정지·급락 판정
- 시간축 샘플

부분 요약의 종료 시각도 비정상 현재 카운터가 아니라 마지막 유효 카운터 시각을 사용합니다. 긴 중단 구간이 정상 관찰 시간처럼 보이지 않도록 하기 위한 경계입니다.

## 구조화 종료 원인

시간 연속성이 끊기면 다음 종료 원인을 사용합니다.

```text
TimingDiscontinuity
```

이전에 유효한 샘플이 있으면 일반적으로 다음처럼 기록됩니다.

```text
status: PartialSuccess
terminationReason: TimingDiscontinuity
```

첫 후속 카운터부터 0·음수 또는 과도한 간격이면 유효 샘플이 없으므로 `status=Failed`가 될 수 있습니다. 자동 분석에서는 `status`와 `terminationReason`을 함께 확인하며, 직접 원인은 `TimingDiscontinuity`입니다.

통합 로컬 보고서의 고정 Finding은 다음 코드를 사용합니다.

```text
BROWSER_OBSERVATION_TIMING_DISCONTINUITY
```

## 사용자 취소·NIC 오류와 구분

| 종료 원인 | 의미 |
|---|---|
| `CanceledByUser` | 사용자가 명시적으로 중지 |
| `AdapterChanged` | Native WLAN 물리 인터페이스 ID 변경 |
| `AdapterUnavailable` | 고정 NIC Down·제거 또는 통계 조회 불가 |
| `CounterProviderMismatch` | 고정 ID와 카운터 공급자 불일치 |
| `TimingDiscontinuity` | 같은 고정 NIC의 카운터 시각 간격이 허용 범위를 벗어남 |

시간 단절은 인터페이스가 달라졌다는 뜻이 아닙니다. 같은 NIC라도 장시간 수집이 멈췄다면 실시간 처리량 표본으로 사용할 수 없다는 의미입니다.

## 오탐 완화

일시적인 CPU 부하나 스케줄러 변동 때문에 관찰이 지나치게 자주 중단되지 않도록 다음 여유를 둡니다.

- 최소 상한 5초
- 예상 간격의 최대 4배까지 허용
- 경계값과 같은 간격은 허용
- 경계값을 실제로 초과한 경우에만 중단

500ms 또는 1초 샘플에서 2~4초 정도의 일시 지연은 허용하지만, 5초를 넘긴 구간은 브라우저 다운로드의 실시간 처리량 샘플로 사용하지 않습니다.

## 주입식 end-to-end 검증

`IBrowserObservationRuntime` 합성 런타임으로 실제 장치나 외부망 없이 다음 전체 흐름을 검증합니다.

### 유효 샘플 뒤 5초 초과 간격

```text
초기 카운터
  ↓ 0.5초
유효 샘플 1
  ↓ 0.5초
유효 샘플 2
  ↓ 5.001초
비정상 카운터 — 결과에 포함하지 않음
```

기대 결과:

- `Status=PartialSuccess`
- `TerminationReason=TimingDiscontinuity`
- 유효 샘플 2개만 유지
- 부분 요약 종료 시각은 두 번째 유효 카운터 시각
- 통합 보고서 `terminationReason` 유지
- `BROWSER_OBSERVATION_TIMING_DISCONTINUITY` Finding 생성

### 첫 샘플의 0초 간격

기대 결과:

- `Status=Failed`
- `TerminationReason=TimingDiscontinuity`
- 샘플과 요약 없음
- 0초 구간의 바이트 델타 미포함

## 통신·데이터 경계

시간 연속성 정책은 이미 로컬에서 얻은 두 `DateTimeOffset` 값과 예상 샘플 간격만 비교합니다.

다음 작업은 수행하지 않습니다.

- DNS 조회
- HTTP/HTTPS 요청
- PAC/WPAD 또는 프록시 연결
- 외부 API 또는 AI
- 텔레메트리·자동 오류 전송
- 결과 업로드

합성 테스트 역시 실제 Native WLAN·NetworkInterface·외부망을 사용하지 않습니다.

## 실제 환경 검증

1. 500ms 또는 1초 간격으로 정상 관찰을 완료하고 `Completed`를 확인합니다.
2. 높은 CPU 부하로 2~4초 지연이 발생해도 즉시 중단되지 않는지 확인합니다.
3. 테스트·디버그 환경에서 5초를 초과해 카운터 수집을 멈추고 `TimingDiscontinuity`를 확인합니다.
4. 중단을 유발한 카운터의 바이트가 시간축과 통계에 들어가지 않는지 확인합니다.
5. 통합 JSON·CSV·HTML과 관찰 전용 보고서에서 종료 원인이 동일하게 표시되는지 확인합니다.
6. 사용자 중지, NIC 변경·제거와 시간 단절이 서로 다른 종료 원인으로 구분되는지 확인합니다.

실제 사내 SSID·BSSID·인터페이스 GUID·IP·MAC·프록시·PAC 주소는 공개 Issue나 테스트 fixture에 원문으로 남기지 않습니다.
