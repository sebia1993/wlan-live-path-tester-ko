# 브라우저 관찰 샘플 시간 연속성

브라우저 관찰은 연속된 Wi-Fi 인터페이스 누적 바이트 카운터의 차이를 실제 시간 간격으로 나눠 Mbps를 계산합니다. 절전, 드라이버 정지, CPU 과부하, 디버거 중단 또는 운영체제 스케줄러 지연으로 샘플 간격이 지나치게 길어지면 하나의 정상 구간처럼 계산해선 안 됩니다.

`WM_POWERBROADCAST` 절전 메시지를 처리하더라도 일부 Modern Standby·드라이버·가상화 환경에서는 메시지가 늦거나 누락될 수 있습니다. 따라서 관찰 러너는 각 카운터 스냅샷의 실제 시각 차이도 별도로 검증합니다.

## 고정 규칙

예상 샘플 간격은 기존 관찰 옵션과 같은 500~2000ms 범위입니다.

```text
허용 상한 = max(5초, 예상 샘플 간격 × 4)
```

예시:

| 예상 간격 | 허용 상한 | 판정 예시 |
|---:|---:|---|
| 500ms | 5초 | 5초까지 유지, 5초 초과 중단 |
| 1000ms | 5초 | 5초까지 유지, 5초 초과 중단 |
| 1500ms | 6초 | 6초까지 유지, 6초 초과 중단 |
| 2000ms | 8초 | 8초까지 유지, 8초 초과 중단 |

0 또는 음수 시간 간격도 중단합니다. 이는 운영체제 시각이나 카운터 타임스탬프가 역행한 상태에서 음수·무한대 처리량이 계산되는 것을 방지합니다.

## 처리 순서

```text
고정 물리 Wi-Fi 카운터 읽기
  ↓
이전 Timestamp와 현재 Timestamp 비교
  ├─ 0 이하 → 중단
  ├─ 허용 상한 초과 → 중단
  └─ 허용 범위 → 바이트 차이·Mbps 계산
```

중단 판정은 현재 스냅샷을 시간축 샘플에 추가하기 전에 수행합니다. 따라서 비정상적으로 긴 간격의 바이트 델타가 평균·최고·총 수신량에 포함되지 않습니다.

## 구조화 종료 원인

시간 연속성 보호로 중단되면 다음 값을 기록합니다.

```text
terminationReason: TimingDiscontinuity
```

기존에 유효한 샘플이 있으면 `PartialSuccess`, 하나도 없으면 `InterfaceUnavailable` 또는 실패 상태가 될 수 있습니다. 정확한 해석에는 `status`와 `terminationReason`을 함께 봅니다.

화면에서는 다음처럼 표시합니다.

```text
종료 원인: 샘플 시간 연속성 중단 (TimingDiscontinuity)
```

브라우저 관찰 전용 JSON·CSV·HTML 보고서에도 같은 구조화 값이 저장됩니다.

## `SystemSuspend`와 차이

| 종료 원인 | 근거 |
|---|---|
| `SystemSuspend` | Windows 창이 명시적인 절전 전환 메시지를 수신함 |
| `TimingDiscontinuity` | 전원 메시지 여부와 무관하게 실제 카운터 샘플 간격이 허용 상한을 초과함 |

절전 메시지가 정상적으로 먼저 도착하면 `SystemSuspend`를 우선 사용합니다. 메시지를 받지 못했지만 복귀 후 첫 카운터 간격이 길다면 `TimingDiscontinuity`가 데이터 혼합을 막는 보조 안전망입니다.

## 오탐 완화

일시적인 CPU 부하나 스케줄러 지연 때문에 정상 관찰이 지나치게 자주 중단되지 않도록 다음 여유를 둡니다.

- 최소 허용 상한 5초
- 예상 간격의 최대 4배까지 허용
- 상한과 정확히 같은 간격은 허용
- 상한을 초과한 경우에만 중단

5초 이상 GUI 또는 카운터 수집이 멈췄다면 그 구간은 실시간 브라우저 처리량 추정으로 사용하기 어렵다고 판단합니다.

## 통신·데이터 경계

시간 연속성 검사는 이미 로컬에서 수집한 두 타임스탬프만 비교합니다.

다음 작업은 수행하지 않습니다.

- DNS 조회
- HTTP/HTTPS 요청
- PAC/WPAD 또는 프록시 조회
- 외부 API 호출
- 타임스탬프·관찰 결과 업로드
- AI·텔레메트리·자동 업데이트

## 실제 환경 검증

1. 1초 샘플 간격으로 정상 관찰을 완료하고 `Completed`를 확인합니다.
2. CPU 부하를 잠시 높여 2~4초 지연이 생겨도 즉시 중단되지 않는지 확인합니다.
3. 관찰 중 Windows 절전을 실행하고 `SystemSuspend` 또는 보조 안전망인 `TimingDiscontinuity` 중 하나가 기록되는지 확인합니다.
4. 디버거·테스트 환경에서 카운터 읽기를 5초 넘게 중단해 `TimingDiscontinuity`를 확인합니다.
5. 중단을 유발한 긴 간격의 바이트 값이 평균·최고 처리량에 포함되지 않는지 확인합니다.
6. 관찰 전용 JSON·CSV·HTML에서 종료 원인이 구조화돼 있는지 확인합니다.
7. 일반 사용자 중지가 `TimingDiscontinuity`로 오인되지 않는지 확인합니다.

실제 SSID, BSSID, 인터페이스 GUID, IP, MAC, 프록시 주소와 PAC URL은 공개 Issue에 원문으로 남기지 않습니다.
